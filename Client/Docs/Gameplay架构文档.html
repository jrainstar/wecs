Step()（Stage.cs:364）是逻辑帧核心：

Assets/Scripts/GameLogic/Gameplay/Logic/Core/Stage.cs : 364public void Step()
{
    if (StageState.Ticking != info.state) return;
    var tick = info.timescale * GAME_DEFINE.LOGIC_TICK;
    info.frame++;
    info.elapsed += tick;

    // Tick 驱动
    foreach (var type in TICK_DEFINE.TICK_TYPE_LIST) { ... behavior.Tick(时间) ... }

    // 帧末调度
    foreach (var type in TICK_DEFINE.TICK_TYPE_LIST) { ... behavior.EndTick() ... }

    Recycle();
}
  • TICK_TYPE_LIST 是显式登记的执行顺序（TICK_DEFINE.cs：Gamepad → Facade → RILSync），新加 Behavior 必须登记，否则不会被 Tick。
  • Recycle() 统一回收：Behavior 先 Disassemble()，再出表、回对象池。

diff 的门槛：frame <= 1 直接丢弃

Stage.Diff() 开头有一道拦截：

Assets/Scripts/GameLogic/Gameplay/Logic/Core/Stage.cs — Diff// 初始化阶段的增量一律丢弃，等首次 Translate() 的全量同步覆盖
if (0 == info.frame || 1 == info.frame) return;
条件拦截的内容原因
0 == info.frameBuilding() 里 18 个英雄的 DIFF_NEWInitialize() 期间 frame 仍是 0。这批增量会被首次 Translate() 的全量 IRIL 完全覆盖，提前发给渲染层只会让 diff 找不到可合并的已有 RIL
1 == frame第一个逻辑帧 Tick 内产生的 diffStep() 的 frame++ 在 Tick 之前，所以首帧内部看到的是 1；此时仍早于 EndTick 的全量翻译，同样没有意义
可读性问题：info.frame 与 frame 是同一个属性，写法不统一，建议合并为 info.frame <= 1。更稳的语义是加一个 private bool synced;，首次 Translate() 后置位，Diff() 判断 if (false == synced) return;，这样恢复/重连场景也能复用同一套语义。

Translator：Info → RIL

Translator<T, E>.OnRIL(info) 的执行流程：

Assets/Scripts/GameLogic/Gameplay/Logic/Translators/Common/Translator.cs : 131protected override void OnRIL(BehaviorInfo info)
{
    // 1. once 短路：只处理一次的 Translator 直接跳过
    if (once && rileds.Contains(info.actor)) return;
    // 2. 哈希去重
    var result = CacheHashCode(info);
    if (false == result.diffed) return;
    // 3. 记录已处理（仅 once）
    if (once) rileds.Add(info.actor);

    var ril = RILCache.Ensure<E>();
    ril.Ready(info.actor, result.hashcode);
    OnRIL(info as T, ril);
    stage.rilsync.Send(ril);
}

哈希的存储与比较：

Assets/Scripts/GameLogic/Gameplay/Logic/Translators/Common/Translator.cs : 151protected (bool diffed, int hashcode) CacheHashCode(BehaviorInfo info)
{
    int hashcode = OnCalcHashCode(info as T);
    if (stage.rilsync.Query(info.actor, id).Equals(hashcode)) return (false, hashcode);
    stage.rilsync.CacheHashCode(info.actor, id, hashcode);
    return (true, hashcode);
}
  • key 是 (actor, id) 元组，每个 Actor 的每种 RIL 各存一份，SpatialInfo 与 FacadeInfo 互不干扰。
  • 哈希在 Send() 之前就写入（第 155 行 vs 第 143 行）。若 OnRIL(info, ril) 抛异常，哈希已更新但 RIL 没发出去，下一帧算出相同哈希会跳过，渲染层永久收不到这次更新。OnRIL 里新增可能返回 null 的查表逻辑时要留意。

once 开关

protected virtual bool once => false;，为 true 时用 rileds（HashSet<ulong>）记录已推送的 Actor，后续帧在第一步就短路，连哈希都不算。Actor 被移除时 RmvOnce(actor) 会从 rileds 里删除，允许重建后再推一次。

Translatoronce每帧行为
ActorTranslatortrue首帧算哈希推送，之后靠 rileds 直接短路
StageTranslatorfalse每帧算哈希，frame / actorcnt / behaviorcnt 变化才推
SeatTranslatorfalse每帧算哈希，座位表变化才推
SpatialTranslatorfalse每帧算哈希，位置 / 旋转 / 缩放变化才推
TickerTranslatorfalse每帧算哈希，timescale 变化才推
FacadeModelTranslatorfalse每帧算哈希，model 变化才推

RILSync：出口

OnEndTick() → Translate()（每个逻辑帧末执行一次）：

Assets/Scripts/GameLogic/Gameplay/Logic/Behaviors/Stage/RILSync.cs : 224SendLossRIL();                                  // ① 先发 RIL_LOSS
foreach (var kv in info.behaviorinfos)             // ② 逐类型、逐 Info 翻译（IRIL）
    ...translator.Translate(behaviorinfo)...

while (diffqueue.TryDequeue(out var diff)) { ... stage.ondiff?.Invoke(clone); }    // ③ DIFF
while (eventqueue.TryDequeue(out var evt)) { ... stage.onevent?.Invoke(clone); }   // ④ EVENT

四个步骤的先后顺序是强约束：

顺序内容为什么必须在这个位置
①SendLossRIL()RIL_LOSS 与普通 IRIL 共用 rilqueue，必须先入队才能保证渲染层「先删后建」
②遍历 behaviorinfos 翻译产生全量 IRIL；StageInfo 排在最前，RIL_ACTOR 才能先于任何 Actor 级 RIL 到达
③排空 diffqueuediff 是增量的「补丁」，必须建立在已有 IRIL 之上
④排空 eventqueue事件通常依赖当前状态已就位
关于并行：此处早期用 Parallel.ForEach，现已改为普通 foreach。并行版的问题：入队顺序不确定，RIL_LOSS 与同 Actor 的 IRIL 可能乱序到达渲染层（导致 Agent 建了又被回收）；且 Query 未加锁，与 CacheHashCode 的写操作并发会破坏 Dictionary。改单线程后这两类风险消失，hashcodedict 上残留的 lock (@lock) 已成为冗余。
注意：Translate() 内的翻译逻辑不能碰 UnityEngine——它由逻辑帧（FixedTickEvent）驱动，与渲染帧无关。

SendLossRIL：撤销指令

负责把逻辑层删掉的 BehaviorInfo 转成 RIL_LOSS，通知渲染层丢弃对应类型的渲染状态。

Assets/Scripts/GameLogic/Gameplay/Logic/Behaviors/Stage/RILSync.cs : 190private void SendLossRIL()
{
    foreach (var rmvbehaviorinfo in stage.cache.rmvbehaviorinfos)
    {
        if (stage.SeekBehavior(rmvbehaviorinfo.actor, out Tag tag, true) && tag.Get(TAG_DEFINE.ACTOR_TYPE, out var val))
        {
            if (val == ACTOR_DEFINE.FLOW) continue;      // 逻辑 Actor 无渲染状态
        }

        if (false == translatordict.TryGetValue(rmvbehaviorinfo.GetType(), out var translators)) continue;
        foreach (var translator in translators)
        {
            var ril = RILCache.Ensure<RIL_LOSS>();
            ril.Ready(rmvbehaviorinfo.actor, 0);
            ril.loss = translator.id;

            translator.RmvOnce(rmvbehaviorinfo.actor);        // 清 once 标记
            hashcodedict.Remove((rmvbehaviorinfo.actor, translator.id), out _);  // 清哈希
            RmvHashCode(ril.actor, ril.loss);
            Send(ril);
        }
    }
}

为什么需要它：Translate() 只翻「当前存活」的 Info（if (false == behaviorinfo.active) continue;），Info 被删时渲染层收不到任何信号。全量快照只能表达「有什么」，没法表达「少了一个」，删除必须靠显式撤销指令。

渲染层如何响应

Assets/Scripts/GameLogic/Gameplay/View/Resolvers/Common/RILBucket.csif (ril.id == RIL_DEFINE.LOSS)
{
    // 1. 通知 Enchant（如 ModelEnchant 回收 ModelAgent）
    foreach (var enchant in enchantdict[loss]) enchant.LossRIL(loss);
    // 2. 删表
    iddict.Rmove(loss);                  // 按 RIL ID 删
    rildict.Remove(ril.GetType());       // 按类型删
    return;
}

三个容易漏的点

  1. 一个 Info 可能发多条 LOSS：FacadeInfo 同时挂了 FacadeModelTranslator 和 FacadeAnimationTranslator，内层 foreach (var translator in translators) 每条只撤销一个 translator.id。
  2. 必须清 hashcodedict：不清的话，同一 Actor 重新添加同类型 Info 时，若新哈希与旧值相同会被判为「无变化」而跳过发送，渲染层永久缺失该状态。
  3. 必须清 rileds（通过 translator.RmvOnce(actor)）：否则 once = true 的 ActorTranslator 会因 Actor 仍在集合里而永远不再推送。

时序隐患

SendLossRIL() 排在 foreach 之前，靠「先入队」保证渲染层先删后建。这个顺序是隐式约定——如果把它挪到翻译之后，RIL_LOSS 会晚于新 IRIL 入队，渲染层就会「先建后删」，把刚建好的状态又删掉。

RIL_LOSS 与普通 IRIL 共用 rilqueue，单线程入队 + FIFO 出队 ⇒ 渲染层的删除/重建顺序与逻辑层一致。这个正确性依赖两点：SendLossRIL() 在 Translate() 里先于翻译执行，以及翻译本身是单线程的。

脆弱点：RIL_ACTOR 必须先于任何 Actor 级 RIL 到达渲染层，目前靠「StageInfo 在 behaviorinfos 中排在第一个」这一结构约定，代码里没有断言。调整 ManualTranslators() 顺序或 Stage 加 Behavior 顺序时要小心。

常见问题定位

现象优先检查

新增一个渲染字段的完整步骤

  1. XxxInfo 加字段，更新 OnReady / OnReset / OnClone
  2. XxxTranslator.OnCalcHashCode 把新字段纳入哈希（否则变了也不发）
  3. XxxTranslator.OnRIL(info, ril) 填充 RIL 字段 + RIL 的 OnReady / OnReset 初始化
  4. Agent 里 WatchRIL<Xxx> 或对应 Enchant 里消费
  5. 若涉及新 RIL 类型：RIL_DEFINE 加 ID → RILSync.ManualTranslators() 注册 → 需要增删 Agent 则 RILBucket.Enchants() 注册 Enchant
